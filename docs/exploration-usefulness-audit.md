# Diagram usefulness audit

Ground rules for this pass: every item below traces to something observed in
actual rendered output (fresh SVGs/HTML generated from the two fixture pairs,
the committed reference PNGs in `test/snapshots/reference/`, and the
README-embedded `docs/sample-*.svg`), cross-checked against the source that
produced it. Nothing here is a code-quality or doc-hygiene complaint for its
own sake — see each item's "why it matters" for the concrete effect on what
a reviewer sees. Ordered roughly by how much each would change what you
actually see/understand reviewing a real PR.

Three known issues are being fixed in parallel elsewhere and are excluded
here even where they overlap: view-mode naming/labels, clustered-view
directory diff-color accuracy, and diff-focused collapse granularity for
deeply-nested subdirs.

---

## 1. The standalone SVGs — the artifact the README tells you to paste into a PR — have no legend, and removed nodes silently lose their dashed cue

**Where:** `dist/diagram-diff.svg`, `dist/diagram-all.svg`, `dist/diagram-clustered.svg` (generated by `src/renderer/draw.ts`), as opposed to `dist/diagram.html` (generated by the parallel implementation embedded in `src/renderer.html`).

**What I observed:** `README.md` documents `dist/diagram-diff.svg` explicitly as: *"Diff-focused graph (paste as image in PR comment)"*. I generated it fresh for the `users` fixture and grepped for the word "legend" — zero matches in any of the three standalone SVGs. There is no color key anywhere in the file itself.

Worse, the legend that *does* exist (in `diagram.html`'s sidebar) promises removed nodes get a **dashed** border: `border:1.5px dashed #ef4444 — Removed (ghost)`. But the actual removed-node rect in the standalone SVG has no `stroke-dasharray` at all:
```
<rect x="701" y="447" width="206" height="40" rx="4" fill="#8f3539" stroke="#ef4444" stroke-width="1.5"/>
```
This isn't specific to my fresh run — it's already true of the committed, README-embedded reference image: `docs/sample-diff.svg`'s `DashboardNavComponent` (a removed node) also renders with a solid, undashed border. Anyone who has looked at the README sample has already seen this.

**Root cause:** two independent SVG-rendering implementations exist — `src/renderer/draw.ts` (used for the three standalone `.svg` files) and the client-side JS embedded in `src/renderer.html` (used for the interactive `diagram.html`). The HTML version's JS *does* apply `stroke-dasharray="4,2"` to removed nodes; `draw.ts`'s final node-rendering branch (the one that handles ordinary in-scope/removed-ghost nodes, `draw.ts:146-154`) never sets a dash array on the rect at all. The two renderers have drifted.

**Why it matters:** if you (the sole user) ever use the tool the way the README recommends — grab `diagram-diff.svg` and paste it as an image somewhere — you get a diagram with zero legend, where removed and modified/added nodes are distinguishable *only* by hue, no shape/pattern redundancy, and where the shape cue the interactive version relies on doesn't exist. This is also just an outright inconsistency in what the tool ships: the legend text is a promise the static artifact doesn't keep.

**Recommendation:** either (a) make `draw.ts` apply the same `stroke-dasharray` for `diff === "removed"` nodes that `renderer.html` already does, closing the drift, and/or (b) add a compact inline legend (a small `<g>` of swatches + text) to the standalone SVGs specifically because they're the artifact meant to travel alone.

## 2. The "has unit test" dot is the exact same green as the "Added" node border — on a new, tested component, the coverage marker vanishes into the node's own outline

**Where:** `src/renderer/draw.ts:34` (`TEST_DOT = "#22c55e"`) and `src/renderer.html:224` (`fill="#22c55e"`), vs. `NODE_STROKE.added = "#22c55e"` (`draw.ts:16`) — literally the same hex value.

**What I observed:** the dot is drawn as a 3px-radius filled circle in the node's bottom-right corner, right where the node's own rounded-corner border curves. For any *unchanged* node it reads fine — e.g. `DashboardStatsComponent` in the sample-app reference PNG shows a clearly visible green+purple dot pair against its plain blue-bordered box. But neither fixture happens to produce a node that is both `diff: "added"` *and* `hasTests: true` at the same time (I checked `graph.json` for both fixtures — the only node with `hasTests`/`hasStories` set is `UserCardComponent`, which is unchanged in this diff), so this specific combination has never actually been rendered and looked at. Given the color values are identical, a green-bordered added component with a passing unit test will render its test-coverage dot nearly indistinguishable from its own diff outline — right at the exact moment (spot-checking whether new code has test coverage) the marker exists to help with.

**Why it matters:** this marker only earns its keep on changed nodes — checking coverage on unchanged files isn't really a PR-review question. But changed nodes are exactly where the color collides.

**Recommendation:** pick a color for the coverage/story dots that doesn't overlap the diff palette (green/orange/red), e.g. a neutral white/gray or the existing purple-family alongside a non-green second color.

## 3. Unchanged context edges have the same visual weight as diff edges, and there are a lot of them

**Where:** diff-focused view, `users` fixture (`test/snapshots/reference/diff-focused.png`, confirmed fresh in `dist/diagram-diff.svg` — 109 total edges).

**What I observed:** `edgeColor()`/rendering apply full `opacity="1"` and `stroke-width="1.5"` to added, modified, *and* unchanged edges alike — only `removed` edges get `opacity="0.5"`. In the rendered diff-focused view, the majority of the 109 edges are unchanged (blue `#8fa8d6`) context edges connecting nodes that aren't part of the diff at all, and they crisscross the whole canvas at the same weight as the green/orange/red diff edges. Visually scanning the screenshot, the actual diff signal is a minority of the ink on the page — you have to actively filter out a dense mesh of same-weight blue lines to find what changed.

**Why it matters:** the entire point of diff-focused mode is "show me what changed." Right now the layout does that (only diff-relevant subtrees are expanded), but the *edge rendering* doesn't reinforce it — nothing distinguishes "this edge is why you're looking at this diagram" from "this edge is just context."

**Recommendation:** dim and/or thin unchanged edges (e.g., the same `opacity: 0.5` or lower already used for removed edges, maybe combined with `stroke-width: 1`), so added/modified/removed edges read as the figure and unchanged edges read as the ground.

## 4. The change-magnitude gradient lives only in the fill color, which is subtle; the border — the thing you actually notice — doesn't encode magnitude at all

**Where:** node fill computation, `nodeFill()`/`nodeColor()` (`src/renderer.html:118-123`, `src/renderer/draw.ts:72-84`); `users` fixture, four modified nodes.

**What I observed:** I pulled the real magnitude values and rendered hex colors for all four `modified` nodes in the `users` fixture:

| Node | linesChanged | magnitude | rendered fill | rendered border |
|---|---|---|---|---|
| `UserTableHeaderComponent` | 1 | 0.025 | `#30405a` (≈ unchanged `#2d3f5c`) | `#f59e0b` (full-strength orange) |
| `UserDetailComponent` | 4 | 0.1 | slightly warmer | `#f59e0b` |
| `UserSettingsComponent` | 11 | 0.275 | noticeably warmer | `#f59e0b` |
| `UsersListComponent` | 63 | 1.0 | `#9a5510` (full "modified" color) | `#f59e0b` |

The fill *does* gradient correctly (confirmed: `UserTableHeaderComponent`'s fill is `#30405a`, barely distinguishable from the plain "unchanged" fill `#2d3f5c` — appropriate for a 1-line edit). But the border — a thin 1.5px stroke, which is what your eye actually catches first on a small box against a dark background — is `#f59e0b` at full saturation on *all four*, with no magnitude interpolation at all. Practically: a reviewer scanning the diagram sees "four orange-bordered boxes," full stop; the fill difference that's supposed to convey "this one's a one-line tweak, that one's a 63-line rewrite" is a background-tint distinction on small nodes that's easy to miss, especially against the dark theme.

**Why it matters:** the fixture was explicitly built to "demonstrate the change-magnitude gradient" (per `CLAUDE.md`), and the underlying data is right — but the piece of the rendering that dominates visual perception (the border) isn't part of the gradient, so the feature under-delivers relative to what it's for.

**Recommendation:** either extend the `lerpHex` interpolation to the stroke color too (e.g. lerp from `unchanged` stroke to `modified` stroke by magnitude, same as the fill), or use a second channel (border width, e.g. 1px→3px) to carry magnitude instead of relying on fill alone.

## 5. "Modified import" (amber edges) has never actually been rendered anywhere the user has looked

**Where:** edge-diff computation, `src/diff-parser.ts:100-112`; `Edge Legend` in `src/renderer.html:76-80`.

**What I observed:** an edge is classified `modified` only when the *same* `fromFile→toFile` edge exists in both base and current, but the set of imported names differs (e.g. `import { Foo } from './x'` becomes `import { Foo, Bar } from './x'`). I checked: `dist/graph.json` for **both** fixtures has zero edges with `diff: "modified"` — every edge is `added`, `removed`, or `unchanged`. Neither fixture, and therefore neither the committed `docs/sample-*.svg` reference images nor the visual-regression PNGs, has ever shown what an amber "modified import" edge actually looks like in practice.

**Why it matters:** adding a name to an existing import statement is an extremely common real-world PR pattern — probably more common than adding a brand-new edge. This is a real edge-legend category (1 of 4) that's shipped but effectively unverified by anything visual in this repo.

**Recommendation:** not a rendering fix, just a verification gap worth closing cheaply — add one modified-import case to a fixture (e.g. add a second named import to an existing `UsersService` import somewhere) so the amber edge color has actually been seen and checked at least once.

## 6. In-scope node labels carry no file path — only out-of-scope nodes show one

**Where:** node label rendering, both `draw.ts` and `renderer.html`; in-scope branch (`draw.ts:146-154`) draws only `label`, no path. There's also no hover tooltip (`title` attribute) on in-scope `<g class="node-group">` elements.

**What I observed:** an out-of-scope node like `PermissionsService` renders two lines — the class name and, in smaller muted text, `shared/services`. An in-scope node like `UserSettingsComponent` renders *only* the class name; `node.file` (`src/app/features/users/user-settings/user-settings.component.ts`) is present in `graph.json` but never surfaces anywhere in the diagram or on hover.

**Why it matters:** for the fixture's flat, uniquely-named files this doesn't bite. But in a bigger real feature — the kind of thing a reviewer actually opens this tool for — it's plausible to have two same-named files in different subdirectories (or just want to confirm which file a box refers to without cross-referencing `graph.json` by hand).

**Recommendation:** add a `<title>` element (native SVG tooltip, no JS needed even in the static files) with the full `node.file` path on hover.

## 7. `docs/spec.md`'s "Planned"/"Non-goals" sections misstate two things that materially affect what to expect from the tool today

Per instructions, only including items where the gap changes what a reviewer/user should expect, not doc-hygiene for its own sake.

- **"Out-of-scope grouping" is listed as unimplemented ("Planned") but is fully built and working correctly today.** I confirmed directly: in the `users` fixture, `shared/guards` (2 nodes, both unchanged) and `shared/components` (3 nodes, all unchanged) and `shared/api` (1 node, unchanged) each collapse into a single `● dir (n)` pill — while `shared/services` (7 nodes) stays fully expanded, because 2 of its 7 members (`AuthService`, `NotificationService`) are diff-touched this PR. That's not an inconsistency — it's the collapse rule working exactly as designed (`src/renderer/graph-helpers.ts:10-12`: *"Out-of-scope parent dirs where every node is unchanged → one stub per dir"*), correctly keeping the directory expanded specifically because it contains diff-relevant signal. Worth knowing this already ships and works well, since spec.md says otherwise.
- **"Type-only import detection" is listed as unimplemented, but partially exists.** Nodes already render specially (italic label, dashed border, distinct fill `#22385e`) when *every* incoming edge is type-only (`src/analyzer.ts:328-338`). What's genuinely missing is edge-level styling — a single type-only edge among a node's other normal edges renders identically to a value import.
- **Non-goals says CI integration is "out of scope for this repo"** — contradicted by the working `.github/workflows/diagram.yml` + `action.yml`. Concretely, what you'd actually experience: the PR comment does **not** embed an inline diagram image the way the "Planned" section's own description of the future Action says it eventually would (*"posts `diagram.svg` as an inline PR comment image"*) — it posts a text summary (added/modified/removed counts + file list) plus a link to an artifact-hosted `diagram.html`, and that link "expires with artifact retention" (`src/action/comment-body.ts:57`). So don't expect an inline image in the PR thread itself — you always have to click through.

## Scope limitation

Both fixtures are deliberately small (59 and 10 in-scope nodes). I looked for a larger, messier real Angular repo on this machine to stress-test layout at real scale (hundreds of files, deep nesting, high fan-out) — none was available (`~/code` doesn't exist, no other checkouts found). As a substitute I ran the tool against this repo's own `src/` directory (the same thing `.github/workflows/diagram.yml` already does on every PR to this repo, using an older commit as a synthetic base for a real 8-modified/1-added diff) — but that codebase is itself only 11 non-test files, too small to exercise the same concerns. So: layout scalability, edge-crossing density, and label collision at real-world scale remain unverified by this audit, one way or the other — not a finding, just a genuine gap in what this pass could check.
